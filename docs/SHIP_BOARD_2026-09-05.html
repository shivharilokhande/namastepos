What shipped

E-invoice & e-way bill stop fabricating numbers

done

generateIrn() computed a correct NIC SHA256 but never called the IRP, so every IRN in production was fabricated — and Advanced is sold at ₹999 partly on “e-invoice”. A restaurant filing against one of those has a tax problem, not a software problem. New irpGateway.js refuses in production instead of falling back to the stub. Outside production the demo survives but is branded at the value, the row and the document: DEMO-NOT-A-VALID-IRN-… is neither 64 hex nor 12 digits, so it cannot be typed into a portal.

Migration 093 also created the columns migration 046 only thought it created — 024 had already made eway_bills, so 046’s CREATE TABLE IF NOT EXISTS was a silent no-op and POST /eway-bills had been a 500 in every environment.

Copy corrected, and a guard so it stays correct

done

Every plan mention now reads “e-invoice ready (GSP connection required)” — landing page, four commercial pages, llms.txt, the dashboard and the Flutter billing screen. The feature key stays: it gates a capability that genuinely exists, and pulling it would revoke access from paying tenants to fix a sentence. The claims guard gained a notion of credential-gated features, so a claim like this now fails CI unless the copy carries the qualifier. The old guard compared copy to feature keys and could not see “key exists, integration is a stub”.

Voice POS re-enabled

done

The blocker was stale twice over: connectivity_plus is ^7.3.1 now, and speech_to_text 7.x dropped package:js for dart:js_interop. Resolved clean, nothing forced, nothing downgraded. Real OS recognisers, a prompt-free probe so opening New Order never throws a permission sheet, and honest degradation for each failure — no recogniser, denied, offline, silence, unsupported locale.

Not oversold: mixed Hindi/English recognition is not reliable. Default locale is en_IN rather than hi_IN, because Devanagari output cannot match a menu row stored in Latin script. So nothing reaches the cart without a tap — the confirm sheet shows the transcript, flags low-confidence guesses and lists what it could not match. Realistically a fast path for a few high-frequency items, not hands-free ordering.

iOS stops offering a printer flow that cannot work

done

Apple gates classic Bluetooth, and the cheap 80mm printers Indian restaurants actually own are not MFi — but iOS was showing the Android scan screen anyway. An owner tapped scan, got an empty list, and concluded the app was broken. iOS now explains why in one plain sentence and offers what works: AirPrint and share-to-PDF, via the printing dependency already in the tree. Android is untouched.

The print-agent queue is described but deliberately not linked: it carries kitchen tickets only, never customer bills, and nothing issues the agent token yet. A button there would have been a second dead end.

Found on the way out

The audit trail was fire-and-forget

fixed

CI failed on one assertion after the first push: mark-paid returned 201, the next test read audit_log, and the row was not there. The same suite passed 786/786 locally. Not a flaky test. middlewareLog wraps the synchronous res.json and called log() without awaiting it, so the client was told the action succeeded while the INSERT was still in flight. A process exiting in that window drops the record entirely — and the error was swallowed by a bare catch with no logging, so the trail could stop recording for days and still look complete.

The regression test asserts the ordering, not a timing: the wrapped res.json must not reach the underlying send synchronously. Verified in both directions — restored to fire-and-forget it fails deterministically, which the two row-existence tests alone did not, because on a fast local database a fire-and-forget INSERT usually wins the race. That luck is exactly what let this reach CI.
