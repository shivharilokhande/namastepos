## Important correction to the brief
`subscriptions.status` has no CHECK constraint, but it IS the Postgres ENUM `subscription_status` (`db/migrations/002_saas_schema.sql:18`, values trialing/active/past_due/paused/cancelled/expired — every write casts `::subscription_status`). A new `'suspended'` value therefore **needs migration 094** (`ALTER TYPE … ADD VALUE IF NOT EXISTS`). Verified with the real runner (`node scripts/migrate.js` on a scratch DB, transactional, PG 14.23): applies and re-runs idempotently; the new value is not used inside the same file (Postgres forbids that within the adding transaction).

## Shared mechanism introduced (used by A1/A3/A4)
- `razorpayService.checkoutMode({ requireLive })` → `'gateway' | 'manual' | 'unavailable'`. Prod: live key + webhook secret → gateway, else `unavailable` (503 `PAYMENTS_UNAVAILABLE`, never free). Non-prod: plan paths (`requireLive:true`) need a `rzp_live_` key + webhook secret (identical to the rule billingController had since 2026-08-26); addon paths need any key (identical to the old `razorpayConfigured`). `manual` = instant activation, non-prod only. billingController, subscriptionService.resume, churnService.resume and addonService now all ask this one function.
- `subscriptions.reactivation_rzp_subscription_id` (094): `createSubscription` stamps the NEW gateway sub id there (and repoints `razorpay_subscription_id` BEFORE cancelling the old sub, closing a webhook race). `_onChargeSuccess` lets exactly that id's first charge reactivate a cancelled / cancel-at-period-end / paused row (marker consumed); any other charge on such a row is recorded but never reactivates (the 2026-08-30 guard stays). Side benefit: the pre-existing "cancelled tenant re-subscribes via checkout → charged but never activated" hole is closed (test `A1 rebuy`).

Nothing in the API claims otherwise. Proper fix options: (a) create the new Razorpay subscription with `start_at = current_period_end` and let the old one run out (simplest, fair, no credit maths — the same `startAt` plumbing I added for undo-cancel), or (b) Razorpay `addons` / offer for a one-off credit. Decision needed on which.
2. **Razorpay `start_at`**: undo-cancel (A1) now creates the new subscription with `start_at` = current period end (only when >1h away) so the customer is not billed twice for the same days. Please verify once in Razorpay test mode that the authorisation checkout + deferred first charge behaves as documented for UPI Autopay/cards before relying on it; if not wanted, remove the `startAt` argument in `subscriptionService.resume` and the charge happens immediately.
3. **Suspend does not touch the mandate**: an admin-suspended paid tenant keeps being debited (charges are recorded, service stays off). Decide: cancel at cycle end on suspend, or refund on restore.
4. **Paid addon cancel is immediate** (`addonService.cancel` ends the period at NOW(), a 2026-08-24 decision from the free-addon era). With paid addons this forfeits paid days; resume can no longer give them back (A2). Consider cancel-at-period-end for paid addons (revoke already does this).
